# 解析器维护手册

本文档定义新网页抓取、日常分析反馈、问题报告、诊断、修复、回归和发布的标准流程。

## 1. 正常使用流程

```text
打开 HTTP/HTTPS 内容页面
→ 等待正文加载完成
→ 点击 Content Catcher
→ 开始抓取
→ 检查标题、作者、正文首尾和图片数
→ 复制或下载 Markdown
```

动态页面只解析当前已经渲染的 DOM。扩展不绕过登录、付费墙、浏览器保护或网站权限。

需要模型分析时，点击“复制给模型”并粘贴到自行选择的模型，直接在同一对话中提出修改意见。模型按提示核对原文、修订相关部分；无需先进入调试模式。

用户偏好在默认折叠的“分析设置”中手动保存；聊天里的“以后都这样”不会自动同步到插件。记录问题也不是普通修订的必经步骤。

分析完成且值得长期保留时，点击“复制收藏指令”，将其粘贴回包含抓取原文和最终分析的同一对话。收藏入口与抓取状态无关，只复制指令；它不代表已经写入 Obsidian。

## 2. 什么情况需要报告

- 正文缺失、过短或抓取失败。
- 混入导航、侧边栏、评论、推荐或推广。
- 标题、作者、账号、时间或来源错误。
- 图片丢失、仍是占位图或链接无效。
- 标题层级、列表、引用、代码或表格转换错误。
- 尾部过早截断，或者没有截断站点噪声。

## 3. 最小问题材料

报告至少包含：

```text
URL：
浏览器可见的预期结果：
导出的实际结果：
Content Catcher 版本：
```

如果 Markdown 无法说明 DOM 问题，解析完成后点击“导出脱敏诊断样本”，附上生成的 JSON。提交前仍应人工检查诊断文件，不要提供密码、Cookie、Token、个人信息或不应公开的数据。

诊断 schema v3 应满足：正文和尾部文案没有原文残留；所有远程 URL 指向 `example.invalid`；安全占位文本保持原文本长度；`selection`、`metadata` 和 `content.cleanup` 摘要存在，`content.cleanup.stages` 记录 `structure`、`placeholder-images`、`noise`、`site-tail` 四个阶段的计数，不保存被删除的原文。诊断仅包含选中的正文根节点，外围候选使用无文本的结构与评分摘要表示。清理比例不是正文缺失率；需结合抓取稿和合成 fixture 定位具体缺失，不能仅凭比例认定误删。

## 4. 问题分类

先判断修改应该落在哪里：

| 类型 | 判断依据 | 修改位置 |
| --- | --- | --- |
| 通用解析 | 多个网站可能发生；涉及语义节点或候选评分 | 通用选择/评分逻辑 |
| 站点结构 | 固定域名、稳定正文节点或站点元数据 | `SITE_ADAPTERS` |
| 通用转换 | DOM 选对了，但 Markdown 标签转换错误 | Markdown 转换逻辑 |
| 站点清洗或转换 | 站点特有推荐、尾部 CTA 或视觉标题 | 适配器 `cleanup` / `transform` |
| 诊断能力 | 问题无法从脱敏样本复现 | 诊断 schema 与隐私测试 |

默认优先修通用能力；只有可证明的站点差异才进入适配器。

## 5. 建立回归样本

1. 从脱敏诊断中截取最小必要 DOM。
2. 将普通正文改成虚构文本。
3. 删除无关节点和属性。
4. 保留触发问题的嵌套、选择器、懒加载属性和噪声位置。
5. 保存到 `tests/fixtures/<site-or-case>.html`。
6. 在 `tests/extractor.test.mjs` 中先添加失败断言。

Fixture 必须离线、确定、最小，不得包含完整真实文章、凭据、Cookie、跟踪参数或私人地址。

## 6. 实施规则

- 选择器优先使用语义标签、稳定 id 和公开结构。
- 不依赖明显随机生成的 class，除非存在回退路径。
- 新站点适配器保持小型，只包含匹配、正文根、元数据和额外清洗。
- 通用规则必须在至少一个通用 fixture 上得到验证。
- 删除规则必须验证“噪声被删除”和“最后一个真实段落仍保留”。
- 图片规则必须覆盖 `src`、`data-src` 等实际使用的懒加载属性。

## 7. 本地验证

分析适用性规则只允许使用通用、稳定、已经存在的解析指标。新增或调整规则前必须证明问题会显著影响模型分析，并为触发和不触发场景各增加回归断言。提示必须是建议性的，不能改变解析结果或阻断导出；界面最多显示两个提示。

模型交接契约的语义修改需要更新对应提示版本、ADR 和有意义的离线测试。`evidence-v4` 测试覆盖通俗中文、少术语、短段落的内置默认，偏好只覆盖相应表达维度，完整主张与推导区分、按证据类型判断、独立验证核对、不强制等级、具体且不重复的见解，以及集中说明限制。空 `preferences`、设置存储键、函数接口与后续反馈的明确保存条件保持不变。文本断言只验证规则与数据已写入交接输入，不验证外部模型表现。

抓取上下文、字段缺失降级、正文原样保留、偏好与反馈路径的数据边界继续回归。定位索引须验证 `B0001` 起始、包含 frontmatter 的一基行号、只跳过闭合的首部 frontmatter、完整代码块、前 48 个 Unicode 码点与仅 `trim` 的摘录，以及 JSON 尖括号转义和正文只拼接一次。用合成材料覆盖标题、段落、列表、引用、表格、图片引用及伪造边界标签，不保存真实文章全文。

诊断与上下文回归须确认 schema v3 的阶段顺序、计数来源和白名单投影：模型输入只保留合法阶段的 `{ rule, removedElementCount, removedTextLength }`，不把被删除文本或额外字段带入模型输入；缺失旧字段应安全降级。现有就绪提示的触发与不触发行为保持不变。`archive-v2` 测试覆盖原文直接呈现、保留内部代码与元数据、区分聊天交付包装和文件内容，并继续覆盖材料缺失、目录边界、重复冲突、不覆盖和失败降级。设置测试覆盖旧配置补默认值、持久化、恢复默认、非法路径和存储失败，普通复制与下载不受影响。

离线文本测试只证明输入被正确构造，不证明模型一定忠于原文、理解偏好或成功保存。功能交付不依赖付费模型调用，也不要求为每次反馈反复跑多个模型。若按需进行语义观察，使用合成文章或不入库的真实材料，记录模型、提示版本与观察限制；单次结果不能证明通用改善，旧模型的问题也不能直接归因于新模型。

以下四个独立案例均为合成材料，不含真实文章，逐例执行状态为**待验证**。本次另用一份覆盖这四类问题的组合材料，在当前会话中完成 `evidence-v3` 与 `evidence-v4` 各一次定性观察：两个版本均识别主要证据缺口，新版解释了更多术语、减少等级标签，但输出未明显缩短，不能据此认定整体质量提升。未接入外部模型 API；四个独立案例、偏好覆盖的实际模型表现和用户选用的外部模型仍需按需验证，不作为默认必跑或付费测试。

1. **概念与效果分开**。材料：“评测分为规则检查与效果验证，两者职责不同；采用这个分类后，项目效果提高了。”未提供效果数据。成功：分别说明分类是否清楚、效果提升尚无依据，不强制打等级。失败：仅因没有实验否定分类，或由分类合理直接认定项目有效。
2. **完整强主张、一致率与选规数据**。材料：“新规则已普遍优于旧规则并消除数据泄漏；重复判断一致率从 55% 到 85%。每轮都用同一验证集选分数最高的规则。”未说明最终独立测试。成功：保留完整主张，区分一致与正确，指出选规数据不能同时证明独立效果；未交代的隔离步骤只标为无法确认。失败：把主张缩成“判断更一致”就认可优越性，或仅凭流程名称断言没有泄漏。
3. **不同决策对应不同动作**。材料：“准备上线的操作可能误发通知，方案是先小范围运行；训练样本中存在标签冲突，方案是先复核冲突样本。”成功：分别给出上线范围控制与训练样本复核的动作，说明各自依据和风险边界；必要推导作出标记。失败：列出多条“加强评测、持续优化”的重复建议，或让局部工程清单替代两个主要决策。
4. **通俗化但保留条件**。材料：“只有在未参与训练和规则选择的测试样本上，正向结果才能支持泛化判断。”成功：默认用短段落解释为“换一批没用于训练或挑规则的数据再检查”，保留“未参与规则选择”等条件；偏好仅写“用英文”时只改变语言，未指定维度仍沿用默认。失败：保留术语却不解释，或为简短改成“再测一次就能证明有效”，或把语言偏好当作取消证据要求。

观察时记录模型、提示版本、偏好、对应索引位置及是否满足判据；未运行不写“通过”。观察结果只说明该次输入和输出，不据此宣称 `evidence-v4` 提升了所有模型的分析效果，也不自动扩充默认规则。真实文章不保存进案例库。

```bash
npm ci
npm test
npm run check:static
git diff --check
```

需要分发包时再运行：

```bash
make package
```

真实浏览器相关测试由人工维护者负责，包括扩展加载与重新加载、真实页面抓取、弹窗布局、剪贴板和下载。Agent 负责上述离线检查与按需打包，并在交付时列出本次涉及的人工检查项；除非用户明确重新分配，不主动操作真实浏览器。等待人工结果属于交接项，不作为 Agent 浏览器工具缺失的阻塞。

人工真实网页验证至少检查元数据、正文首尾、章节结构、图片数量和导出文件。

代码与层级修复需要精确比较合成 fixture 中的代码载荷，包括 `BR`、高亮注释、缩进、空行、尾随空格及围栏字符；标题提升必须同时验证微信正例、通用和微信列表、编号段落与歧义内容的反例。人工验收需确认预览只读且仍可选择复制，并检查三个导出入口对应的原始内容一致。索引变更还需把“复制给模型”粘贴到本地编辑器，抽查块编号和行号能定位到同一份抓取稿，且扩展版本、抓取时间、清理阶段计数和正文边界正确；无需发送给模型。

弹窗设置变更还应由人工在重新加载扩展后检查：设置位于页头下方且默认折叠；三项设置保存后重开仍保留；未保存草稿不影响复制；两个目录的非法输入都有明确提示；恢复默认生效。在首次打开、抓取中、成功和失败状态分别检查“复制收藏指令”可用，粘贴后核对目录与 `archive-v2` 内容，并确认成功提示只表示已复制。再将普通复制、复制给模型的内容粘贴到本地编辑器核对并检查下载的 Markdown；无需发送给模型。未收到人工结果时标记“待人工验证”；收到后按实际结果记录通过或问题，不用 jsdom 结果代替真实剪贴板、下载或布局验证。

## 8. 轻量反馈与提示维护

普通反馈先在当前模型对话中解决：检查是事实错误、证据不足还是表达偏好，核对原文后给出相关修订。用户意见没有原文支持时应说明依据，不能为迎合意见补造结论。

用户明确要求“把这次问题记下来”时，具有文件能力的模型按交接指令向配置目录保存一份 Markdown。默认目录为 `/Users/chenghao/Documents/Code/content-catcher/.content-catcher/runs`，文件使用 UTC 时间加短随机标识，避免覆盖。只记录来源、已知模型与提示版本、问题片段、用户意见、核对依据、修订结果；未知版本为 `unknown`，不保存全文、完整对话或隐含推理。默认目录被 Git 忽略，公开前仍需删减、脱敏。

无文件能力或写入失败时，模型应说明未保存并在聊天提供记录内容，不影响修订、不另选目录。扩展不能观察模型聊天或确认文件存在，维护者须检查实际文件，不能把提示中的保存要求当作成功证明。

按需阅读记录时，分别处理：

- 确定的工程缺陷，如漏段、提示丢失、配置无效：建立离线回归后修复对应代码。
- 用户明确的长期偏好：整理为一句偏好，由用户手动保存；不改所有人的默认规则。
- 默认要求与产品用途不符：按明确的产品决策简化或调整契约；优先替换、合并规则，保留版本与 ADR 记录。
- 某次模型失误或模型升级后的差异：先保留案例；没有足够证据时不判断为共性，不自动添加提示补丁。

反馈文件不自动注入未来分析，不触发评分、重复模型测试或自动优化。用户每次提出意见不等于需要修改提示词；已有回归只针对已经确定的工程行为。必要时检查历史案例有助于定位，但不形成默认的付费评测流程。

## 9. 按需收藏文章

收藏只在用户主动复制 `archive-v2` 指令并交给已有文章分析对话后发生。扩展不携带页面内容，不知道当前对话对应哪篇文章，也不访问配置的 Obsidian 目录。多篇文章指向不明、缺少抓取原文或缺少最终分析时，外部模型应先询问，不从网络补全。

模型生成的单份 Markdown 包含来源、作者、收藏日期、收藏理由、最终阅读笔记和原样抓取稿，区分原文与推导并保留证据限制。原文单独成节，直接作为 Markdown 正文呈现，不额外包裹整篇代码围栏或整体缩进；保留原有元数据、代码块及空白。聊天交付时为复制使用的外层代码围栏不写入实际文件，保存后核对原文格式。未知信息标为 `unknown`；远程图片链接不等于文件备份，禁止自动下载图片。文件按模型环境中的日期命名为 `YYYY-MM-DD 文章标题.md`，并清理非法文件名字符。

写入前只检查配置目录内的同来源或同名笔记。发现重复或无法确认冲突时必须先询问，不覆盖、合并或修改已有笔记。无文件能力或写入失败时说明未保存，并给出可手动保存的 Markdown；不更换目录，不执行 Git 提交或推送。扩展不会自动创建目录或确认写入成功，实际路径和 Git 同步状态分别由执行模型与人工维护者核实。

`archive-v2` 与 `evidence-v4` 分开维护。修改收藏目的、笔记构成、冲突处理或安全边界时，只升级收藏提示版本并更新 ADR 与专项测试；收藏目录不得进入日常分析提示，收藏规则也不得增加抓取权限或网络能力。

### 收藏成品验收

验收目标是资料能可靠保存、回查和使用。先判断是否满足这个用途，再列改进项；在本次检查范围内没有阻断问题，就明确判定“通过”。发现可以改进的地方，不等于收藏不合格。

- **必须处理的阻断问题**：存错文章，缺少抓取原文、最终阅读笔记或关键内容，重要结论失真，把推测写成事实并影响理解，或未经授权覆盖已有内容等，导致资料保存、回查或使用不可靠的问题。指出具体位置、证据和实际影响。
- **不阻断使用的改进项**：局部排版、重复表述、非关键元数据待确认，以及不影响核心理解的补充信息。按需要简要说明，不作为必须整改项，也不为凑数提出建议。

严重程度按实际影响判断。例如，局部图示排版不佳通常不阻断；如果已经无法读出影响结论的关键关系，则应说明其影响并按阻断问题处理。原有的来源、原文留存、证据区分和不覆盖要求继续有效。

回复先给验收结论及依据，再说明必要问题；关键材料不足以判断时，明确待确认项，不猜测。原文格式检查区分额外的整篇代码块包装和原文自带的代码块：前者按用户要求移除，后者保留。修正指定笔记时核对包装内原文保持不变，不批量迁移其他笔记。Chrome 收藏指令复制与 Obsidian 阅读视图待人工验证。只有成品可检查时，结论限于成品，不据此声称已经核对原始抓取字节、验证写入过程或完成外部事实核查。

改进意见优先在当前笔记或用户偏好中处理。确定的工程缺陷按回归流程修复；不因单次瑕疵自动扩充提示词，不引入评分或重复模型测试。这套约定用于项目内审阅，不附加到每次分析或收藏提示中。

## 10. 版本与发布

- 用户可见的解析、界面或权限变化：更新 `extension/manifest.json` 版本和 `CHANGELOG.md`。
- 纯文档或测试维护：通常不提升扩展版本，但仍需清晰提交记录。
- 提交使用 `feat:`、`fix:`、`test:`、`docs:` 等聚焦前缀。
- 推送后确认 GitHub Actions 通过。
- 用户重新加载解压扩展后才能使用新版本。

## 11. 完成标准

一个解析问题只有同时满足以下条件才算解决：

- 最小合成 fixture 可以复现原问题。
- 新断言能够防止问题重新出现。
- 全量解析测试、静态检查和 diff 检查通过。
- 未引入真实文章、敏感数据或不必要权限。
- 版本与变更记录在需要时已经更新。
- GitHub Actions 为绿色。
