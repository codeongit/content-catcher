# 解析器维护手册

本文档定义新网页抓取、问题报告、诊断、修复、回归和发布的标准流程。

## 1. 正常使用流程

```text
打开 HTTP/HTTPS 内容页面
→ 等待正文加载完成
→ 点击 Content Catcher
→ 开始抓取
→ 检查标题、作者、正文首尾和图片数
→ 复制或下载 Markdown
```

动态页面只解析当前已经渲染的 DOM。扩展不绕过登录、付费墙、浏览器保护或网站权限。

## 2. 什么情况需要报告

- 正文缺失、过短或抓取失败。
- 混入导航、侧边栏、评论、推荐或推广。
- 标题、作者、账号、时间或来源错误。
- 图片丢失、仍是占位图或链接无效。
- 标题层级、列表、引用、代码或表格转换错误。
- 尾部过早截断，或者没有截断站点噪声。

## 3. 最小问题材料

报告至少包含：

```text
URL：
浏览器可见的预期结果：
导出的实际结果：
Content Catcher 版本：
```

如果 Markdown 无法说明 DOM 问题，解析完成后点击“导出脱敏诊断样本”，附上生成的 JSON。提交前仍应人工检查诊断文件，不要提供密码、Cookie、Token、个人信息或不应公开的数据。

诊断 schema v2 应满足：正文和尾部文案没有原文残留；所有远程 URL 指向 `example.invalid`；安全占位文本保持原文本长度；`selection`、`metadata` 和 `content.cleanup` 摘要存在。诊断仅包含选中的正文根节点，外围候选使用无文本的结构与评分摘要表示。

## 4. 问题分类

先判断修改应该落在哪里：

| 类型 | 判断依据 | 修改位置 |
| --- | --- | --- |
| 通用解析 | 多个网站可能发生；涉及语义节点或候选评分 | 通用选择/评分逻辑 |
| 站点结构 | 固定域名、稳定正文节点或站点元数据 | `SITE_ADAPTERS` |
| 通用转换 | DOM 选对了，但 Markdown 标签转换错误 | Markdown 转换逻辑 |
| 站点清洗 | 站点特有推荐、尾部 CTA 或视觉标题 | 适配器 `cleanup` |
| 诊断能力 | 问题无法从脱敏样本复现 | 诊断 schema 与隐私测试 |

默认优先修通用能力；只有可证明的站点差异才进入适配器。

## 5. 建立回归样本

1. 从脱敏诊断中截取最小必要 DOM。
2. 将普通正文改成虚构文本。
3. 删除无关节点和属性。
4. 保留触发问题的嵌套、选择器、懒加载属性和噪声位置。
5. 保存到 `tests/fixtures/<site-or-case>.html`。
6. 在 `tests/extractor.test.mjs` 中先添加失败断言。

Fixture 必须离线、确定、最小，不得包含完整真实文章、凭据、Cookie、跟踪参数或私人地址。

## 6. 实施规则

- 选择器优先使用语义标签、稳定 id 和公开结构。
- 不依赖明显随机生成的 class，除非存在回退路径。
- 新站点适配器保持小型，只包含匹配、正文根、元数据和额外清洗。
- 通用规则必须在至少一个通用 fixture 上得到验证。
- 删除规则必须验证“噪声被删除”和“最后一个真实段落仍保留”。
- 图片规则必须覆盖 `src`、`data-src` 等实际使用的懒加载属性。

## 7. 本地验证

```bash
npm ci
npm test
npm run check:static
git diff --check
```

需要分发包时再运行：

```bash
make package
```

真实网页手工验证至少检查元数据、正文首尾、章节结构、图片数量和导出文件。

## 8. 版本与发布

- 用户可见的解析、界面或权限变化：更新 `extension/manifest.json` 版本和 `CHANGELOG.md`。
- 纯文档或测试维护：通常不提升扩展版本，但仍需清晰提交记录。
- 提交使用 `feat:`、`fix:`、`test:`、`docs:` 等聚焦前缀。
- 推送后确认 GitHub Actions 通过。
- 用户重新加载解压扩展后才能使用新版本。

## 9. 完成标准

一个解析问题只有同时满足以下条件才算解决：

- 最小合成 fixture 可以复现原问题。
- 新断言能够防止问题重新出现。
- 全量解析测试、静态检查和 diff 检查通过。
- 未引入真实文章、敏感数据或不必要权限。
- 版本与变更记录在需要时已经更新。
- GitHub Actions 为绿色。
